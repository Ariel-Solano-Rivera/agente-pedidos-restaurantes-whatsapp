# Contratos HTTP v1

Base: `/api/v1`. Autenticación HTTP Basic de demostración; no usar fuera del entorno local. El usuario autenticado determina restaurante y rol. Todas las respuestas de error usan `{ "code", "message" }`; `code` es un identificador estable (por ejemplo `ORDER_NOT_FOUND`, `FORBIDDEN`, `VALIDATION`) y no incluye el número HTTP. Un 401 devuelve `UNAUTHORIZED` y el mensaje `Usuario o contraseña incorrectos.` sin encabezado `WWW-Authenticate`, para que el panel muestre el error en su formulario y no active un diálogo nativo del navegador.

| Operación | Actor | Entrada / salida | Errores |
|---|---|---|---|
| `GET /me` | cualquier rol | usuario, restaurante y permisos | 401 `UNAUTHORIZED` en JSON, sin `WWW-Authenticate` (sin credenciales o con credenciales incorrectas) |
| `GET /dashboard` | ADMIN, CAJA, COCINA | resumen aislado: restaurante, estado de recepción, fecha, plato más vendido, máximo tres tareas programadas y `cash {collected, receivable}` de hoy (`null` para COCINA) | 401 |
| `GET /dashboard/admin?range=TODAY\|LAST_7_DAYS\|LAST_30_DAYS` | ADMIN | indicadores con `{current, previous}` frente al período anterior de igual duración, ventas no concretadas por causa, pedidos por hora, platos y extras top, retiro/entrega, derivaciones abiertas, platos agotados y retrocesos por día y rol; definiciones en `backend/sdd/resumen-negocio.md` | 400 `RANGE_INVALID`, 401, 403 |
| `GET /menu/categories`, `GET /menu/catalog/presentations`, `GET /menu/catalog/ingredients`, `GET /menu/dishes`, `GET /menu/dishes/{id}` | cualquier rol | menú y catálogos del restaurante actual; cada plato incluye `active` (visibilidad) y `available` (calculado por el backend: alguna variante activa, no agotada y con unidades libres si `tracked`); cada variante incluye `tracked` | 401, 404 |
| `GET /menu/dishes/{id}/image` | cualquier rol | imagen binaria del plato propio, si existe | 401, 404 |
| `POST/PUT/DELETE /admin/categories/{id?}` | ADMIN | categoría validada; el borrado solo procede sin platos asociados | 400, 403, 404, 409 |
| `POST/PUT/DELETE /admin/catalog/presentations/{id?}`, `POST/PUT/DELETE /admin/catalog/ingredients/{id?}` | ADMIN | elemento reutilizable de catálogo; borrar no altera copias existentes en platos o pedidos | 400, 403, 404, 409 |
| `POST /admin/dishes` | ADMIN | plato, variantes, extras y retirables con IDs activos y propios de categoría, presentación e ingrediente | 400, 403, 409 |
| `PUT /admin/dishes/{id}` | ADMIN | cuerpo `{categoryId,name,description,presentationId,price,extras:[{ingredientId,surcharge,active}],ingredients:[{ingredientId,removable}]}`; cambia datos y reemplaza extras/retirables de un plato propio en una transacción; listas vacías eliminan esas opciones | 400, 403, 404, 409 |
| `PATCH /admin/dishes/{id}/active` | ADMIN | cuerpo `{ active }`; activa o desactiva un plato propio | 403, 404 |
| `DELETE /admin/dishes/{id}` | ADMIN | elimina plato propio, imagen, opciones, disponibilidad y variantes; se rechaza si hay movimientos de disponibilidad | 403, 404, 409 |
| `POST /admin/dishes/{id}/image` | ADMIN | `multipart/form-data` con `file` JPEG/PNG/WebP hasta 2 MB; reemplaza la imagen previa | 400, 403, 404, 413 |
| `GET /operation/settings`, `PUT /admin/operation/settings` | cualquier rol / ADMIN | consulta o actualiza pausa de recepción | 400, 403 |
| `GET /operation/zones`, `POST /admin/zones`; `GET /operation/schedules`, `POST /admin/schedules` | cualquier rol / ADMIN | zonas, tarifas y horarios | 400, 403 |
| `GET /branding`, `GET /branding/logo` | ADMIN, CAJA, COCINA | marca propia `{primaryColor, secondaryColor, hasLogo, updatedAt, contrast[]}` (contraste WCAG AA contra `#FFFFFF`); logo binario | 401, 404 `LOGO_NOT_FOUND` |
| `PUT /admin/branding`, `POST /admin/branding/logo`, `DELETE /admin/branding/logo` | ADMIN | colores `#RRGGBB`; logo `multipart` `file` PNG/JPEG/WebP validado por contenido, hasta 2 MB; auditado; devuelve la marca | 400 `COLOR_INVALID`/`LOGO_INVALID_TYPE`/`LOGO_EMPTY`, 403, 413 `LOGO_TOO_LARGE` |
| `GET /availability`, `POST /availability/adjustments` | ADMIN, CAJA (la lectura hoy no restringe rol: ver `backend/sdd/operacion.md`) | disponibilidad o ajuste con clave idempotente; el ajuste quita `sold_out` y activa el control de cantidad | 400, 403, 404 |
| `PUT /availability/dishes/{dishId}/sold-out` | ADMIN, CAJA | cabecera `Idempotency-Key` (UUID); cuerpo `{ soldOut }`; marca o quita «agotado» en todas las variantes del plato propio, auditado en `audit_log`; respuesta `{dishId, soldOut, variants}` | 400 `IDEMPOTENCY_KEY_REQUIRED`, 403, 404 `DISH_NOT_FOUND` |
| `GET /orders?status&fulfillment&paymentStatus&range&from&to&q&sort&page&size` | ADMIN, CAJA, COCINA | página `{items,page,size,total}`; `range` = `TODAY`, `LAST_7_DAYS` o `CUSTOM` (con `from`/`to`, zona horaria del restaurante); `q` busca por `PED-…`, nombre o teléfono; `sort` = `CREATED_DESC` (por defecto) o `CREATED_ASC`, orden estable por fecha de recepción e id; cada ítem trae `allowedTransitions` y `paymentId` (pago pendiente de confirmar, o `null`). COCINA solo ve estados operativos, sin montos ni pago, y no filtra por pago | 400 `FILTER_INVALID`, 401, 403 |
| `GET /orders/facets?status&fulfillment&paymentStatus&range&from&to&q` | ADMIN, CAJA, COCINA | conteos por opción `{status, fulfillment, paymentStatus, range}` (mapas código → cantidad); cada grupo aplica los demás filtros, no el propio; `range` trae `ALL`, `TODAY`, `LAST_7_DAYS` y `CUSTOM` si llegan `from`/`to`. COCINA: solo estados operativos y `paymentStatus` vacío. Solo lectura, aislado por restaurante | 400 `FILTER_INVALID`, 401, 403 |
| `GET /orders/board` | ADMIN, CAJA, COCINA | `{cards, generatedAt}`: pedidos `ACCEPTED`, `PREPARING` y `READY` (máximo 200) con `publicCode`, modalidad, cliente, hora de retiro, zona, `createdAt`, `statusSince`, unidades y modificaciones **sin importes** y `allowedTransitions` del rol. Solo lectura, aislado por restaurante | 401 |
| `GET /orders/{id}` | ADMIN, CAJA, COCINA | contacto, retiro/entrega, zona, importes (null para COCINA), pago, confirmación, `restaurantDecisionBy`, unidades históricas (una fila por opción elegida: el mismo extra dos veces son dos filas), `allowedTransitions` e `history` con tipo de cambio, motivo, autor y rol | 401, 404 `ORDER_NOT_FOUND` |
| `POST /orders/{id}/transitions` | ADMIN, CAJA; COCINA solo entre `ACCEPTED`, `PREPARING` y `READY` | cabecera `Idempotency-Key`; cuerpo `{ targetStatus, reasonCode?, reason? }`. Retroceder un paso (`PREPARING→ACCEPTED`, `READY→PREPARING`, los tres roles) exige `reasonCode` (`ERROR_AL_AVANZAR`, `CLIENTE_CAMBIO_PEDIDO`, `FALTA_PRODUCTO`, `OTRO`); `reason` es obligatorio con `OTRO` solo para ADMIN y CAJA. Respuesta `{orderId,status,changeType}` (`AVANCE`, `RETROCESO` o `REPETIDO`) | 400 `IDEMPOTENCY_KEY_REQUIRED`/`STATUS_INVALID`/`REASON_*`, 404, 409 `TRANSITION_NOT_ALLOWED` |
| `GET /payments?orderId` | ADMIN, CAJA | pagos del restaurante: `id`, `orderId`, `orderCode`, `method`, `amount`, `status`, `reference`, `verifiedBy` (correo), `verifiedAt`; `orderId` opcional limita a un pedido (otro restaurante: lista vacía) | 400, 401, 403 |
| `POST /payments/{id}/confirm` | ADMIN, CAJA | cabecera `Idempotency-Key`; sin cuerpo; pasa un pago propio `PENDING` o `PENDING_VERIFICATION` a `CONFIRMED` con `verifiedBy` y `verifiedAt`, sincroniza `paymentStatus` del pedido, audita (`PAYMENT_CONFIRMED`) y no cambia el estado del pedido; devuelve el pago. Clave repetida: devuelve el pago sin repetir el efecto | 400 `IDEMPOTENCY_KEY_REQUIRED`, 403, 404 `PAYMENT_NOT_FOUND`, 409 `PAYMENT_NOT_CONFIRMABLE` |
| `GET /handoffs`, `POST /handoffs/{id}/claim`, `POST /handoffs/{id}/release` | ADMIN, CAJA | tomar solo si está `OPEN` o ya es tuya; liberar solo quien la tiene; transacción y auditoría; 204 | 403, 404 `HANDOFF_NOT_FOUND`, 409 `HANDOFF_TAKEN`/`HANDOFF_NOT_HELD` |
| `GET /crm/conversations?tab=PENDING\|HUMAN\|ALL&q&page&size` | ADMIN, CAJA | página de conversaciones con cliente, último mensaje, `awaitingReply` calculado y derivación | 400 `FILTER_INVALID`, 403 |
| `GET /crm/conversations/{id}` | ADMIN, CAJA | conversación, `canReply`, mensajes y ficha del cliente con historial de pedidos | 403, 404 `CONVERSATION_NOT_FOUND` |
| `POST /crm/conversations/{id}/messages` | ADMIN, CAJA con el control | cabecera `Idempotency-Key`; cuerpo `{body}` (1 a 2000); guarda un mensaje `STAFF` sin enviarlo por WhatsApp; 201 | 400, 403, 404, 409 `CONTROL_REQUIRED` |

El panel nunca calcula precios, totales, permisos ni transiciones. Operaciones mutantes incluyen `Idempotency-Key` cuando el reintento pueda producir efectos. Las transiciones y retrocesos están implementados para pedidos sintéticos y no tocan reservas ni pagos (el deshacer de cocina se retiró en el bloque C; `POST /orders/{id}/undo` responde 404); la confirmación manual del pago está implementada (bloque B); creación, reserva, vencimiento y rechazo de pago continúan pendientes de sus contratos.
